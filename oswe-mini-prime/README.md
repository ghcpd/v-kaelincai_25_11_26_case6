# Secure Inputs Audit & Tests

Overview
--------
This workspace contains a security audit and repaired version of a potentially vulnerable Python web app script originally named `inputs.py`. The repository includes:

- `inputs_backup.py` and `input_backup.py`: Backups of the original, vulnerable source.
- `inputs.py`: Patched and secured version of the original script.
- `tests/security_test.py`: Static security checks that look for insecure patterns.
- `run_test.sh`: Unix shell test runner (Linux/macOS).
- `run_test.bat`: Windows batch test runner.
- `auto_test.py`: Cross-platform automation to detect OS and run tests; logs everything to `logs/test_run.log`.
- `requirements.txt`: Python dependencies.
- `Dockerfile`: Docker image for replicating environment and running tests.
- `setup.sh`: Helper to create virtualenv, dependencies and sample DB/data files.

Files generated by the audit
---------------------------
- `report.json`: Vulnerability report detailing all findings and fixes.
- `logs/test_run.log`: Log file generated by `auto_test.py` when running tests.

Setup (Linux/macOS)
-------------------
1. Create a venv and install dependencies:

```bash
bash setup.sh
```

2. Run tests:

```bash
bash run_test.sh inputs.py
```

This will run the static checks against the target file. Use `inputs_backup.py` to test the original file and watch the test fail as expected.

Setup (Windows)
----------------
1. Install dependencies manually or using a virtual environment.
2. Run the Windows test runner:

```cmd
run_test.bat inputs.py
```

Using Docker
------------
1. Build the Docker image:

```bash
docker build -t secure-inputs-audit .
```

2. Run the image:

```bash
docker run --rm secure-inputs-audit
```

Behavior
--------
- Running tests on the original file (e.g. `inputs_backup.py`) should produce a failing test report.
- Running tests on the repaired file (`inputs.py`) should pass.
- `auto_test.py` can be used to detect environment and run the relevant tests automatically, logging output to `logs/test_run.log`.

Notes & Assumptions
-------------------
- Secrets must be provided via environment variables: `THIRD_PARTY_API_KEY`, `DB_PASSWORD`, `JWT_SECRET`, `ADMIN_TOKEN`.
- The backup route is protected via an `X-ADMIN-TOKEN` header that must match the `ADMIN_TOKEN` environment variable.
- The fetch route restricts requests to prevent SSRF by disallowing private IP addresses and `localhost`.

If you need additional integrations, e.g. centralized secret store or proper authentication, I can implement them in a follow-up.
